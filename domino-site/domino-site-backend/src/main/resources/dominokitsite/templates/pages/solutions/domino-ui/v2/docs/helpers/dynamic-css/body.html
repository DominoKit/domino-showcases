Dynamic CSS

Dynamic CSS creates shared Domino UI utility rules at runtime. It is designed for the uncommon application value that cannot be represented by an existing utility class while preserving the same naming, variables, scoping, and reuse behavior as Domino UI’s static utilities.

When to use it

Prefer a well-defined existing Domino UI class whenever one exists. Static classes are more discoverable, communicate intent directly, and keep a shared visual rhythm. Use Dynamic CSS for deliberate, application-owned values such as an exact dashboard width, a design-token fallback expression, or a generated brand color.

Value utilities

The factory naming mirrors the static utility convention. Each call returns a CssClass for use with addCss. String values are passed to the browser without validation; callers must use trusted, valid CSS. Integer overloads are a convenient spelling of the same string value.

  • Spacing: dui_p_, dui_m_, dui_gap_, including axis and side variants.
  • Sizing: dui_w_, dui_h_, and min/max width and height variants.
  • Layout: indent, inset, top/right/bottom/left, z-index, flex basis/grow/shrink/order, and grid tracks.
  • Visual values: border width, radius, outline width/offset, font size/weight, line height, and letter spacing.

Reuse and variables

Dynamic CSS deduplicates by utility definition and source value. Repeating the same factory call returns the same generated class and does not duplicate rules. If a compatible static Domino UI variable already exists, such as a spacing token, the generated rule reuses it instead of defining a second variable.

CSS variable expressions remain expressions; they are not copied or evaluated by Java. A deterministic codec turns them into a safe shared class token, so the generated class can be reused without exposing the expression in a selector.

Dynamic color schemes

dui_clr_ returns a directly usable base color class. For the complete palette, use dui_clr_schm_. A literal color receives generated lighter and darker shades for light and dark mode, then emits the same contextual, foreground, background, border, accent, shadow, outline, and emphasis-compatible utility pattern used by Domino UI’s predefined palettes.

You can also use an application-owned palette reference, for example dui_clr_schm_("var(--dui-clr-my-brand)"). In that case the application must supply the corresponding -l-5 through -l-1, base, -d-1 through -d-4, and foreground variables following Domino UI’s palette convention. Dynamic CSS does not validate color correctness or contrast: choosing and testing the color remains the application author’s responsibility.

Runtime behavior

Dynamic rules are injected into dedicated document style elements, separate from the legacy DynamicStyleSheet implementation. Rules are global to the document but retain Domino UI’s .dui-scoped selectors. The registry shares classes and variables for identical inputs, so using one value across many components does not multiply style rules.

Development and production

Migrated static value utilities resolve lazily in production: only classes retained by the compiled application are injected when used. In Super Dev Mode, the migrated utility registry is preloaded so developers can inspect and experiment with the familiar utility vocabulary in browser tools. Dynamic values themselves are still emitted only when a factory is called.

Safe Dynamic CSS checklist

  • Prefer well-defined static CSS classes before introducing an arbitrary dynamic value.
  • Pass only trusted CSS values; dynamic factory strings are intentionally not validated.
  • Use application variables for values that should react to the active theme.
  • Reuse a scheme object when several components share a generated dynamic color.
  • Check light mode, dark mode, focus, hover, disabled state, and subtle/minimal emphasis for custom colors.
  • Keep app-specific CSS selectors scoped to your Domino UI root.
